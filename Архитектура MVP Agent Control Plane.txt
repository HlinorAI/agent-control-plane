## 1. Архитектурный принцип

MVP строится как **read-only control plane**, а не как inline proxy. Он собирает metadata и ограниченный объём telemetry из разрешённых источников, нормализует сущности, строит граф связей и запускает explainable risk rules.

```text
Sources → Collectors → Normalization → Inventory/Graph → Risk Engine → Findings → Remediation
```

Главный продуктовый outcome — не «собрать логи», а дать доказуемый ответ на вопросы:

- какие агенты работают в production;
- кто их владелец;
- какие модели и providers используются;
- какие identities и tools подключены;
- какие data/system boundaries затрагиваются;
- где есть excessive permissions, shadow agents или отсутствие ownership;
- какое evidence подтверждает каждое утверждение.

## 3. Компоненты MVP

| Компонент | Назначение | MVP implementation |
|---|---|---|
| `agentctl` CLI | Локальный scan и отправка результатов | Go binary, Linux/macOS, JSON output |
| Self-hosted runner | Scan внутри customer network | Docker/Helm, outbound-only HTTPS |
| Source collectors | Git, K8s, Docker, MCP, OTel metadata | 4–5 устойчивых collectors вместо десятков integrations |
| Ingestion API | Приём signed scan batches и OTel metadata | REST/JSON, idempotency keys, tenant auth |
| Job queue | Асинхронный scan/parse/risk pipeline | Redis Streams или NATS JetStream |
| Parsers | Извлечение agent/model/tool/identity entities | Go/TypeScript parsers + schema versioning |
| Normalizer | Приведение framework/provider-specific entities к общей модели | Deterministic transformations |
| Entity resolver | Deduplication и связывание source records | PostgreSQL relationships + confidence score |
| Evidence store | Ссылки на источник утверждения и hash/redaction metadata | S3-compatible object storage + Postgres index |
| Inventory store | Agents, owners, models, tools, identities, environments | PostgreSQL |
| Risk engine | Explainable policy checks | TypeScript/Go rules, YAML definitions |
| Findings service | Severity, lifecycle, evidence, owner, remediation | PostgreSQL + REST API |
| API | Dashboard, integrations, external read API | Go/Fiber или TypeScript/Fastify |
| Web UI | Inventory, graph, findings, scan status | React + TypeScript |
| Integrations | GitHub/Jira/Slack | OAuth/App + outbound webhooks |
| Auth/RBAC | Tenant isolation, SSO, roles | OIDC first; SAML after pilot demand |

## 4. Поток данных

### 4.1 Scan flow

```text
1. User installs agentctl or deploys runner
2. CLI obtains short-lived workspace token
3. Collector reads approved read-only sources
4. Raw local records are redacted and hashed
5. Batch is signed and sent over TLS
6. Ingestion API validates tenant, schema and idempotency key
7. Job is placed in queue
8. Parsers emit normalized entities and evidence refs
9. Entity resolver deduplicates and links entities
10. Inventory snapshot is committed transactionally
11. Risk rules run against changed graph portions
12. Findings are created/updated with evidence
13. Dashboard and integrations receive status
```

### 4.2 Runtime metadata flow

MVP не должен принимать полный production payload по умолчанию. OTel collector отправляет только минимальные metadata fields:

```text
trace_id
agent_id or source fingerprint
model/provider
tool name
environment
service identity fingerprint
timestamp
status/error class
step count / token-cost metadata when available
```

Если customer явно разрешает payload capture, применяется redaction policy и отдельный retention setting. Default — metadata-only.

### 4.3 Remediation flow

```text
Finding created
  ↓
Owner assigned
  ↓
GitHub/Jira issue or Slack notification
  ↓
Customer changes source configuration
  ↓
Next scan detects resolved/changed state
  ↓
Finding closed, reopened or accepted-risk with expiry
```

## 6. Risk rules MVP

Риск-движок должен быть детерминированным и explainable. Каждое правило возвращает `rule_id`, `severity`, `reason`, `evidence`, `affected_entities` и `remediation_hint`.

| Rule ID | Условие | Severity |
|---|---|---:|
| `ACP-001` | Production agent без owner/team | High |
| `ACP-002` | Runtime agent отсутствует в source inventory | High |
| `ACP-003` | Один identity используется несколькими unrelated agents | High |
| `ACP-004` | Agent имеет write/admin tool scope при read-only use case | Critical/High |
| `ACP-005` | MCP server отсутствует в approved registry | High |
| `ACP-006` | Production credential referenced in development | Critical |
| `ACP-007` | Sensitive tool вызывается без approval metadata | High |
| `ACP-008` | Provider/model нарушает workspace policy | Medium/High |
| `ACP-009` | Agent has no documented disable/rollback path | Medium |
| `ACP-010` | Stale agent/identity не проверялся заданный период | Medium |
| `ACP-011` | Duplicate agents выполняют одну capability | Medium |
| `ACP-012` | Tool schema changed без owner acknowledgement | Medium/High |

Для каждого finding в UI обязательно показывать: «почему сработало», «какое evidence использовано», «какой entity affected» и «как проверить/исправить». Не использовать opaque AI-generated risk explanations в критическом пути MVP.

## 7. Рекомендуемый технологический стек

### 7.1 Основной выбор

| Слой | Рекомендуемый стек | Почему |
|---|---|---|
| CLI/runner | **Go** | Один статический binary, быстрый startup, удобный cross-compile, низкий footprint |
| Backend API | **Go + Chi/Fiber** | Единый runtime с collector/runner, простая concurrency model |
| Parsers/rules | **Go**; YAML policy parser | Минимум runtime dependencies, единый типовой контракт |
| Web UI | **React + TypeScript + Vite** | Быстрая dashboard development, graph/filter ecosystem |
| UI components | Tailwind CSS + shadcn/ui | Быстрое создание internal-tool interface |
| API contract | **OpenAPI 3.1** + generated TypeScript client | Contract-first frontend/integrations |
| Primary database | **PostgreSQL 16+** | Transactions, JSONB, relationships, mature managed/self-hosted options |
| Search | PostgreSQL FTS initially; **OpenSearch** later | Не добавлять отдельный cluster до доказанной search load |
| Object storage | S3-compatible: AWS S3 / MinIO | Evidence artifacts, scan reports, encrypted retention |
| Queue | **Redis Streams** initially; NATS later if needed | Простая async pipeline и retry semantics для MVP |
| Telemetry | **OpenTelemetry** | Vendor-neutral traces/metrics/log metadata |
| Policy engine | YAML rules in Go; OPA/Rego only if policy complexity grows | Не тащить OPA до появления customer policy use cases |
| Auth | OIDC; Keycloak for self-hosted; SAML later | Быстрый SSO path и self-hosted option |
| Secrets | Customer-side env/secret manager; platform metadata only | Никогда не хранить raw credential values |
| Packaging | Docker Compose for local; Helm chart for K8s | Local pilot + enterprise deployment |
| CI/CD | GitHub Actions + GoReleaser + Docker Buildx | Release binaries/images for multiple targets |
| Testing | Go test, Testcontainers, Playwright, OpenAPI contract tests | Integration-heavy product needs real source fixtures |
| Monitoring | Prometheus + Grafana + structured logs | Cost-effective self-hosted observability |

### 7.2 Почему не стоит начинать с Python

Python подходит для быстрых parsers и data science, но CLI и self-hosted runner будут распространяться в security-sensitive environments. Статический Go binary снижает friction установки и количество runtime dependencies. Python можно добавить как optional parser worker, если появятся сложные AST/ML workflows, но не делать его обязательным для core path.

### 7.3 Почему не нужна graph database в MVP

Сущности Agent → Identity → Tool → System сначала можно хранить в PostgreSQL через `relationships` table, indexes и materialized views. На масштабе 500–1 000 агентов и десятков миллионов relationships этого достаточно. Neo4j/ArangoDB добавят deployment complexity, backup path и vendor decision до того, как станет понятно, какие graph queries действительно являются differentiator.

## 9. Security architecture

### Trust boundaries

```text
Customer source systems
  → customer-side runner boundary
  → outbound encrypted ingestion boundary
  → multi-tenant control plane boundary
  → integration boundary
```

### Обязательные правила

1. **Read-only by default.** GitHub tokens, cloud roles и Kubernetes service accounts получают только минимальные read scopes.
2. **No raw secrets.** Никогда не принимать и не сохранять values API keys, OAuth tokens, passwords или private keys.
3. **Redaction before upload.** Редактировать credential-like strings, access tokens, personal data и sensitive payloads на стороне runner.
4. **Tenant isolation.** Все tables имеют `workspace_id`; database queries используют application-level guard и, при hosted deployment, PostgreSQL Row-Level Security.
5. **Signed batches.** Runner подписывает batch metadata, а API проверяет workspace-scoped token, nonce, schema version и idempotency key.
6. **Evidence traceability.** Сохранять source locator и content hash, а не весь confidential file по умолчанию.
7. **No arbitrary code execution.** Parser не должен исполнять найденные Python/JavaScript files, Docker commands, MCP tools или IaC.
8. **Outbound-only self-hosted mode.** Runner не открывает inbound port; customer контролирует egress allow-list.
9. **Audit all changes.** Любое изменение owner/status/policy/exception логируется.
10. **Short-lived credentials.** Использовать OIDC/workload identity, где возможно; не просить long-lived personal tokens.

### Threats для MVP

| Threat | Защита |
|---|---|
| Credential exfiltration | Redaction, no raw secret storage, read-only scopes |
| Malicious repository content | Не исполнять код, parse as data |
| Cross-tenant leakage | RLS, workspace-scoped keys, integration tests |
| Poisoned evidence | Hash, source locator, scan signature, provenance |
| Rogue collector | Signed runner release, version allow-list |
| Excessive API permissions | Documented least-privilege scopes and installation checks |
| Finding manipulation | Immutable evidence, audit events, role separation |
| DoS through huge scan | Size limits, timeouts, quotas, backpressure |

## 10. Deployment models

### Mode A: Hosted SaaS

```text
Customer CLI/runner → outbound HTTPS → Multi-tenant Control Plane
```

Подходит для early-stage SaaS и design partners. Customer data retention configurable, default evidence metadata-only. Hosted deployment быстрее для iteration и product analytics.

### Mode B: Self-hosted runner + SaaS control plane

```text
Customer sources → runner inside VPC → outbound encrypted metadata → SaaS
```

Рекомендуемый default для security-sensitive pilots. Raw files и payloads остаются внутри customer environment, наружу уходят normalized metadata, hashes и findings evidence references.

### Mode C: Fully self-hosted control plane

```text
Customer sources → local runner → local API/Postgres/S3/UI
```

Не делать первым deployment target. Поддержать после M4 для 1–2 design partners через Helm chart и documented backup/upgrade path. Full self-hosted сильно увеличивает QA, support и security burden.

## 13. Тестовая стратегия

### Unit tests

Проверять parsers, redaction, schema validation, normalization, entity resolution и каждое risk rule на golden fixtures.

### Contract tests

Проверять OpenAPI API, CLI-to-ingestion batches, schema version compatibility и idempotent re-upload.

### Integration tests

Testcontainers для PostgreSQL, Redis, MinIO; mock GitHub/Kubernetes/MCP sources; real OTel test exporter.

### Security tests

Проверять secret redaction corpus, path traversal, malicious repository fixtures, oversized batches, JWT/OIDC validation, RLS isolation и permission scopes.

### Customer replay tests

Каждый design partner получает redacted fixture pack. Любой parser/rule change прогоняется против fixtures, чтобы не ломать existing inventory и findings.

## 14. Что строить после MVP

После подтверждения WVPA, recurring scans и paid pilots следующий приоритет — MCP Security Gateway: runtime tool policy, approval и action-level audit. Затем добавлять Agent Regression CI, используя накопленные traces и findings для автоматического превращения incidents в regression tests.

Не добавлять следующие функции только потому, что они звучат как «полная платформа»: universal AI firewall, automatic IAM remediation, all-cloud discovery, autonomous remediation agent, full GRC mapping или собственную graph database без доказанной нагрузки.

## 15. Рекомендуемый порядок реализации

2. Git collector + local JSON report
3. Inventory API + PostgreSQL
4. MCP/K8s collectors

## Итоговая рекомендация

Для MVP выбрать **Go + PostgreSQL + S3/MinIO + Redis Streams + OpenTelemetry + React/TypeScript + Docker/Helm**. Архитектура должна оставаться modular monolith с отдельным CLI/runner и async workers, а не набором микросервисов. Это обеспечивает быстрый iteration speed, локальный deployment и понятный security boundary.

Ключевое архитектурное решение — **evidence-first, metadata-only, read-only by default**. Если система не может показать источник каждого relationship и не может безопасно запуститься внутри customer VPC, она не решает основную боль Agent Control Plane.
